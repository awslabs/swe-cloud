Build a program that behaves like the reference command-line tool at `/reference/program`.

The tool reads a JavaScript description of the DNS records a set of zones should contain (`dnsconfig.js`) and a credentials file (`creds.json`). It compares that desired state with the hosted zones in an Amazon Route 53 account and either reports the differences (`preview`) or applies them (`push`). It also validates configurations without contacting AWS (`check`) and exports existing zones in several formats (`get-zones`). A Route 53 emulator is reachable at `http://engines:4566`. `AWS_ENDPOINT_URL` and dummy credentials are already set, and the reference uses them as they are.

Start with `/docs/interface.md`: it gives the invocation, the commands and options in scope, what is out of scope, and exactly which outputs and Route 53 state are compared and how. `/docs/dsl.md` lists the configuration functions you need to support. The guides deliberately leave out how declarations are normalised and validated, how changes are counted, and how existing records are reconciled. Find these out by running the reference against zones you create yourself. Execute the reference to learn its behaviour; do not copy it or decompile it.

Write your source under `/app`, plus an executable `/app/build.sh` that produces `/app/program`. Use any installed language; Python with boto3 and Node.js are available. Only `/app` is kept. Grading runs your build in a fresh environment against a fresh emulator, without `/reference`, `/docs` or any AWS state you created.

The task image's language/toolchain versions and Python packages are recorded in /etc/task-runtime.json before agent setup. Extra runtimes or packages installed by the agent harness are not guaranteed in the verifier. Only /app transfers; build.sh and program run offline as candidate with PATH=/usr/local/bin:/usr/bin:/bin and the AWS endpoint settings of this environment. Use the task-provided tools or bundle additional dependencies under /app and select them explicitly.
