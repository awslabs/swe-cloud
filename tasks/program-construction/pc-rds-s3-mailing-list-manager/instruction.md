Rebuild `list-mailer`, a self-hosted mailing-list and subscriber manager that keeps its state in an RDS PostgreSQL database and stores uploaded media in S3.

A working reference build is installed at `/reference/program`. Run it against the AWS endpoint in this environment (RDS and S3 are available at `AWS_ENDPOINT_URL`) and study what it does. The guides in `/docs` describe the scope: start with `/docs/interface.md` for invocation, configuration, credentials, the AWS setup, which behavior is in scope and how results are compared. `/docs/api.md` lists the HTTP endpoints and `/docs/querying.md` the subscriber query language. The guides are an orientation, not a full specification. Exact semantics, such as how membership statuses change, how bounce rules count, how imports treat existing subscribers, the database schema and how media objects are named, have to be learned by experimenting with the reference.

Write your own implementation in `/app`, in any language available here, and provide `/app/build.sh`. Running it must produce the executable `/app/program`. It must offer the same command-line modes and HTTP API as the reference and leave the same database rows and S3 objects. Only the contents of `/app` are kept for grading. Grading runs `/app/build.sh` in a fresh environment with no network access, where the reference, the documentation and anything you created in AWS are gone, so vendor every dependency you need. You may use the reference only to observe its behavior. Do not copy, unpack or decompile it.

The task image's language/toolchain versions and Python packages are recorded in /etc/task-runtime.json before agent setup. Extra runtimes or packages installed by the agent harness are not guaranteed in the verifier. Only /app transfers; build.sh and program run offline as candidate with PATH=/usr/local/bin:/usr/bin:/bin and the AWS endpoint settings of this environment. Use the task-provided tools or bundle additional dependencies under /app and select them explicitly.
