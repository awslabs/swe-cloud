# Attachment service

The accounts service allocates a unique key, then a client uploads to quarantine. The scanner sends its verdict asynchronously. Downloads are served only from the download bucket. The original presigned upload may arrive even after removal; keys are never reused. Actual virus scanning and URL signing are outside this service.

Start the emulator with `bash /usr/local/bin/start_floci.sh`. Set QUARANTINE_BUCKET, DOWNLOAD_BUCKET, ATTACHMENT_TABLE, SCAN_QUEUE_URL, DELETE_QUEUE_URL and EVENTS_QUEUE_URL. `./attachments provision --prefix desk` creates these resources for local use and prints a JSON environment mapping; export those values for subsequent commands. Existing production resources are provisioned externally. All services use AWS_ENDPOINT_URL, us-east-1, test/test. S3 addressing is path style. The venue supports multipart operations, object metadata, DynamoDB conditions and the PendingExpiry index. CopySourceIfMatch is unavailable here; source reads and ordinary part uploads are supported.

`./attachments allocate --key K` records an allocation. Upload bytes to QUARANTINE_BUCKET/K using an S3 client, then send `{"key":"K","result":"clean"}` to SCAN_QUEUE_URL. Run `./attachments promote-worker` in each scanner-consumer process. A rejected verdict (`result` other than `clean`) cancels staging only; it must never remove a previously ready download.

Run `./attachments delete-worker` for user removals. DELETE_QUEUE_URL accepts `{"key":"K"}`, normally with DelaySeconds=2. Only after removal has finished does it send `{"key":"K","event":"deleted"}` to EVENTS_QUEUE_URL and acknowledge the request. The service objective is to finish within 15 seconds of visibility even if a scan worker is stalled. A failed attempt must not announce success. Unfinished cancellation must remain discoverable for retries and maintenance, including the information needed to stop outstanding storage work. Known cancelled or competing transfers must not leave unfinished multipart uploads. An unresolved network outcome during registration may be left for the bucket's operational incomplete-upload lifecycle policy. The same applies to a transfer that lost registration if its own consumer's abort fails or that consumer dies before aborting it.

All queues are standard queues. Deliveries can duplicate and a consumer can die without acknowledging. Scan visibility is 60 seconds; delete visibility is 5 seconds. Running three promotion processes and one deletion process is normal. Durable coordination belongs in AWS, never a working-directory lock or in-memory registry. A network failure can happen after a storage operation has committed. A new consumer must resume work, not start the same transfer again after publication; duplicate scans must not overwrite the download. No deletion may wait for a paused scan to resume.

The DynamoDB table has a string partition key `path`, formed as DOWNLOAD_BUCKET + '/' + key. Each allocation stores `key`, `state`, `expiresAt`. States are `pending`, `ready`, `deleting`; expiry is an epoch second, initially allocation time + 86400. Allocation is create-only and creates no download object. A ready item has no expiry. A deletion in progress has an immediate expiry. Extra coordination attributes may be added; `uploadId`, when used, identifies registered unfinished storage work and must remain available until that work has been resolved. PendingExpiry is a GSI with hash `state` and numeric range `expiresAt`, projection ALL. No DynamoDB TTL is configured: maintenance owns removal.

`./attachments cleanup --now EPOCH` performs one expiry sweep (default wall-clock now). It must finish expired cancellations and abandoned pending work, and reconcile already-published work whose ready bookkeeping was interrupted. It must leave wanted completed downloads ready with no expiry, even if the expiry index returned an outdated pending view. Ordinary ready downloads survive every sweep. Query results can be stale and paginated.

Workers log failed attempts to stderr and leave messages for retry. A clean, wanted file must eventually have the original bytes in downloads, a ready item without expiry, and no remaining quarantine source or unfinished storage transfer, apart from the transfers left to the bucket lifecycle policy as described above. Empty files are valid attachments. These guarantees must survive concurrent duplicate deliveries, interrupted consumers and lost replies.
