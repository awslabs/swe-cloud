# stepq

stepq is the step queue behind our workflow runs. Items wait in Valkey (an ElastiCache cluster);
executors lease due items, run each item's step by calling the step runner over HTTP, and remove the
item when the step returns. Two fleets share the queue: **the executor fleet** (this repository,
`stepq/executor.py`) and **the batch fleet**, an older service owned by another team. Both call the
same Valkey function library, `stepq/library.lua`, which every executor loads at start with
`FUNCTION LOAD REPLACE`.

```
stepq/
  executor.py   the executor: scan, lease, run, extend, complete, scavenge
  library.lua   the queue function library (q_lease, q_extend, q_requeue, q_dequeue, q_scavenge)
  layout.py     key names
  ulid.py       lease/item IDs
  library.py    loads library.lua
  devstack.py   local cluster, dev step runner, enqueue and status tools
```

## Key layout

| key | type | contents |
|---|---|---|
| `{q}:queue:item` | HASH | item id → item JSON `{"id", "partition", "at", "leaseID", "scavengeCount"}` |
| `{q}:queue:sorted:<partition>` | ZSET | queued items of a partition, score = run-at (ms, shard clock) |
| `{q}:scavenger:<partition>` | ZSET | leased items of a partition, score = lease expiry (ms) |
| `{q}:concurrency` | ZSET | partitions with leased items, score = earliest lease expiry in the partition |

The API enqueues by writing the item JSON (with `"leaseID": null`) and its ready-queue entry in one
`MULTI`, stamping the run-at from the shard's `TIME`.

## Leases

A lease ID is a ULID generated by the caller **before** it calls Valkey; its 48-bit timestamp is the
lease's expiry in milliseconds (`ulid.new(now + ITEM_LEASE_MS)`, `ulid.time_ms(lease_id)`). An item is
leased while its stored `leaseID` is non-null and that timestamp is in the future; its
`{q}:scavenger:<p>` score is that same expiry. Every party (executors, the batch fleet, the ops tooling,
every scavenger pass) reads a lease's expiry from its ID and judges it against the shard's clock. An
executor:

1. scans the ready queues every `POLL_MS` and leases a due item with `q_lease`;
2. calls the step runner (below) with the item and its lease, and waits for the step's outcome
   (steps run from well under a second to minutes);
3. while the step runs, rotates the lease with `q_extend` every `ITEM_LEASE_MS / 2`;
4. on success removes the item with `q_dequeue`; on a failed step puts it back with `q_requeue`.

Every executor also runs a scavenger pass every `SCAVENGE_INTERVAL_MS`: it reads `{q}:concurrency` and
the scavenger indexes for expired leases and calls `q_scavenge` for each such item, so the item of an
executor that died is picked up again by someone else.

## Function contract

The batch fleet and the ops tooling call these with exactly these names, KEYS, ARGV and success codes;
they must keep working for them. `<p>` is the item's partition.

| function | KEYS | ARGV | returns |
|---|---|---|---|
| `q_lease` | `{q}:queue:item`, `{q}:concurrency`, `{q}:queue:sorted:<p>`, `{q}:scavenger:<p>` | itemID, partition, leaseID, nowMS | `0` leased, `-1` not found, `-2` already leased |
| `q_extend` | `{q}:queue:item`, `{q}:concurrency`, `{q}:scavenger:<p>` | itemID, currentLeaseID, newLeaseID, partition | `0` extended, `1` not found, `2` no lease, `3` lease mismatch |
| `q_requeue` | `{q}:queue:item`, `{q}:concurrency`, `{q}:queue:sorted:<p>`, `{q}:scavenger:<p>` | itemID, partition, leaseID, runAtMS | `0` requeued, `1` not found |
| `q_dequeue` | `{q}:queue:item`, `{q}:concurrency`, `{q}:scavenger:<p>` | itemID, partition, leaseID | `0` removed, `1` not found |
| `q_scavenge` | `{q}:queue:item`, `{q}:concurrency`, `{q}:queue:sorted:<p>`, `{q}:scavenger:<p>` | itemID, partition, nowMS | `0` requeued, `1` not found |

`leaseID` arguments are the caller's own lease. Other non-zero codes may be added where a caller has
to tell a new outcome apart; the batch fleet treats anything but `0` as "did not happen".

## The step runner

`POST $STEP_RUNNER_URL/run` with JSON `{"item_id", "lease_id", "executor_id"}` runs the item's step and
answers once the step has ended: `200` if it succeeded, `500` if it failed. `lease_id` names the run: it
is the lease the executor started the run under.

The runner identifies a run by its `item_id` and `lease_id`. A POST naming a pair it has not seen starts
a run. A POST naming a pair it has seen starts nothing: it waits for that run and answers with its
outcome, at once if the run has already ended (the runner keeps outcomes for a day). Once started, a run
is the runner's: it carries on to its end whether or not anyone is still waiting for its answer.

## Running an executor

```
python -m stepq.executor --id E1
```

| env | meaning |
|---|---|
| `VALKEY_URL` | the queue, e.g. `redis://host:6379/0`; executors use nothing else to reach Valkey |
| `STEP_RUNNER_URL` | the step runner base URL |
| `WORKER_SLOTS` | concurrent steps per executor (default 2) |
| `POLL_MS` | ready-queue scan interval (default 100) |

The executor loads the library and then prints `READY` on stdout; nothing is leased before that. In
production executors run as separate processes on separate hosts, several at once; they share
nothing but Valkey. SIGTERM stops an executor gracefully: it stops scanning and waits for its running
steps. Hosts also die without warning.

## Local development

```
eval "$(python -m stepq.devstack up | sed 's/^/export /')"      # dev cluster -> VALKEY_URL
python -m stepq.devstack runner --port 8700 &                    # dev step runner
export STEP_RUNNER_URL=http://127.0.0.1:8700
python -m stepq.executor --id E1 & python -m stepq.executor --id E2 &
python -m stepq.devstack enqueue --count 5
python -m stepq.devstack status
```

## Operating notes and SLOs

- **Dispatch:** a due item starts running (the step runner receives it) within **3 s**.
- **Dead executors:** an item whose executor died is sent to the step runner again by another executor
  within **15 s** of the lease the dead one took, and not before that lease has expired.
- **An item never runs twice.** Steps are not idempotent; apart from the deliberate `q_requeue` after a
  failed step, two runs of one item, at once or one after the other, on one executor or on several, are
  an incident.
- **The shard is shared and sometimes slow.** Connections to it can stall, reset, or drop a reply in the
  middle of a command. Under load, extension and completion calls have been seen taking up to about
  4.5 s to come back. `ITEM_LEASE_MS` is sized for that; it is not a knob for recovery speed.
- **Host clocks.** Executor hosts keep their own time, and it is not the shard's: we have seen hosts up
  to about 4 s off the shard's `TIME`. All queue times (run-at scores, lease expiries,
  `nowMS`) are on the shard's clock; the API and the batch fleet take theirs from `TIME`.
- **The step runner sits behind the platform load balancer**, which gives up on a request it has had no
  answer to for 8 s: it answers the caller `504` and drops the request. The run behind it carries on.
- **Deploys** restart executors one at a time, several times a day: SIGTERM, wait for the process to
  exit, start it again with the same `--id`. The deploy reaches each executor at whatever moment it
  gets there, slow shard or not.
- **The batch fleet** leases, extends and completes items from the same queues through the same
  functions, and runs its own scavenger passes. Scavenger passes (every executor's and the batch
  fleet's) are not coordinated with each other, and each acts on what it read a moment earlier.
