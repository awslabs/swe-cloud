# Account purchase gateway v1

JSON over HTTP on PROVIDER_URL. All endpoints are synchronous. A connection loss
or a worker deadline does not establish whether a purchase took effect. The
service may have committed a purchase before the caller receives its reference.
The account cannot cancel commitments. HTTP errors and lookup failures must not
be interpreted as proof that no purchase exists.

The gateway has a server-side purchase processing limit of 15 seconds from
receipt of the request. By that limit the purchase has either committed or been
permanently discarded; it cannot create a commitment later. Delivery of the
response can remain blocked beyond this limit. Disconnecting a buyer does not
cancel its request or shorten the processing limit. This limit applies to all
three adapters and is independent of the buyer's five-second execution deadline.

POST /purchase accepts `provider_type`, `offering_id`, `count` (positive integer),
and the product-specific fields below, and returns `{"commitment_id":"..."}`.
The reference is generated by the provider and cannot be chosen by the buyer.

| provider_type | optional purchase fields | account behavior |
| --- | --- | --- |
| token | client_token, tags | same token returns the original commitment within 20 seconds of the original commit; afterwards it can buy a new commitment. Tags, if supplied, are committed atomically with the purchase. |
| tag_after | none | purchase accepts neither token nor tags. Tags can be added afterwards in a separate call. |
| none | none | purchase has no idempotency key, tags or describe support. Each successful call creates a fresh commitment. |

POST /tag takes `commitment_id` and `tags` (string map). It is supported only for
`tag_after`. A failed or absent tag call does not roll back the purchase.

GET /describe?provider_type=TYPE&tag_key=KEY&tag_value=VALUE returns a JSON list of
`{commitment_id, offering_id, tags, created_at}`. TYPE may be `token` or `tag_after`.
Only commitments bearing that exact tag are returned. Reads are strongly
consistent, tags are retained indefinitely, and there is no unfiltered account
listing. Missing tags are not synthesized from a request's offering or token.
A `none` request or unsupported purchase fields return HTTP 400.

Buyer correlation convention: tag key `cudly-idempotency-token`; tag value and
native token are lowercase hex SHA-256 of UTF-8 `execution_id:index`. Reuse this
identity throughout the life of a recommendation. Distinct recommendation indexes
must not share a token, even within one order.

For an operator retry, the purchase intent's identity remains that of the
recommendation in the original execution, even though the review/approval has a
new execution ID. The provider does not know about retry rows. A retry must not
renew the native deduplication window or change its correlation identity.
