# Operations

Controllers share the synchronization database, but do not share cluster API visibility. Each deployment is responsible for its own sync_state entries, including entries surviving its previous process. A controller must not mutate another controller's held or pending entries. Workflow execution can continue while the controller is stopped or cannot reach the database. Held entries have no lease or maximum age: an inactive heartbeat changes queue eligibility, never ownership of a running execution's slot. Operators may restart a controller after a crash, using its existing identity.

Our scaled development settings are heartbeat every 2 seconds, inactive threshold 15 seconds, and reconciliation at least every 5 seconds. After a controller becomes ready, or an owned execution becomes reclaimable, abandoned slots should be recovered within 20 seconds. A live queue-front waiter should start within 10 seconds of usable capacity becoming available. These bounds include leftover entries after a restart. Status and synchronization state are separate durable stores; maintenance can interrupt any step. Preserve protection for nonterminal work throughout admission and execution. Workflow cancellation or deletion does not stop an executor that has already started. Queued launch requests may also outlive the workflow API object. Keep capacity reserved until execution has stopped and cannot start later, using the executor interface. For cancelled, deleted or superseded workflows, disable all unstarted node launches and further expansion within 20 seconds of that API change (or readiness, if later), even while another node is running. Recover its reservation within 20 seconds once no payload is running and no payload can start later (or readiness, if later). These bounds apply to the entire finite execution tree; a parent payload finishing does not retire its descendants. Do not impose a fixed grace period: launch delivery has no maximum age and run_seconds is a requested duration, not a safe deadline for cleanup. A replacement at a reused name must drain after its predecessor finishes without inheriting its reservation or completion. On startup a Running workflow whose recorded hold is missing must fail rather than continue without protection.

Database connectivity interruptions may outlast an individual reconnect budget. Retry with bounded backoff and recover heartbeats, admission and release in the same process within 20 seconds after connectivity returns. No supervisor automatically restarts a healthy but disconnected process. The workflow API stays reachable during a database interruption: for a workflow cancelled while its object is still present in the API, the launch and expansion deadline above still runs from that API change. Workflow API failures should likewise be retried, without treating an unavailable API as an empty store.

Incident excerpt, on-call handover:

> After the managed database proxy was recycled, the controller stayed up. Pods finished; waiters kept piling up. One pool normally runs two jobs, but ran one at a time for the rest of the shift. A Failed workflow was still in the API with no synchronization status. SQL still counted it. Manual cleanup restored capacity. A rollout did not clear another pool until an operator found an entry for a workflow already removed from the API.

The executor isn't responsible for cleaning synchronization rows. Never grant a replacement slot on the assumption that loss of controller contact stopped an execution.
